LoopUno: What Can Lossless Diffusion Drafting Buy in One Hour?

Longxuan Yu1, Siheng Xiong2, Greg Ver Steeg11University of California, Riverside  ·  2Georgia Institute of TechnologyProject page  ·  GitHub  ·  Adapters on Hugging Face

Looped language models reuse their layers to gain capability, and they pay for it with slower decoding. Diffusion drafting gives decoding time back. The model guesses several of its own next tokens in one pass and keeps the ones it would have sampled anyway, so the output is unchanged. We propose LoopUno, an adaptation of Uno that brings diffusion drafting to looped transformers, and validate it on the looped agentic model Nanbeige4.2-3B. After one hour of LoRA training the model keeps 2 tokens per step, and function calls decode 2× faster at matching accuracy. Each drafted token is accepted about half of the time, and the first rejection ends the step. This caps the gain near 2.2 tokens per step.

Two recent ideas pull decoding speed in opposite directions.

The first is the looped model. A looped model stores one stack of layers and runs it more than once for every token. Nanbeige4.2-3B[2] stores 22 layers and runs them twice. The loop adds capacity without adding parameters. With 3B parameters the model outperforms 9B and 12B models on agentic benchmarks[2]. The price is time. Every token costs two passes through the stack, so this 3B model decodes as slowly per token as an 8B model.

The second is diffusion drafting. Uno[1] adds a small adapter that drafts several tokens in one pass, in the style of a discrete diffusion model. The original model then checks the draft and keeps the tokens it would have sampled itself. The samples are unchanged by construction. The gain is time: one step can emit several tokens.

A looped model buys capability with time per token. A diffusion drafter buys time back with tokens per step. This post asks whether the two compose. Uno was built for standard layer stacks. In a looped model one adapter has to serve weights that every token uses twice, and the draft has to survive two passes. If the combination works, a looped model keeps its small memory footprint and recovers part of its latency.

Nanbeige4.2-3B gives a second reason to try. It is an agentic model, trained for function calling and code-agent work. Agents are where decoding speed is felt most: one task takes many tool calls, and every call waits on the decoder. Agents are also where a speedup must leave the output alone, because one changed argument breaks a tool call. A lossless drafter fits this setting. So we measure the speedup on function calls and agent trajectories as well as on math, with an adapter that saw only math and reasoning data.

How much speed can drafting buy here? The speedup is the number of tokens a step keeps, divided by the cost of that step relative to a standard one. Training raises the number of tokens kept, and the model's own predictability limits it: a draft is accepted only as often as the model's next tokens can be guessed several positions ahead.

Our budget is one hour on one 8×A100 node. The released Uno adapter for Qwen3-8B used 14.7B training tokens. Ours uses 31M.

Three questions

  1. Does diffusion drafting fit a looped model? We extend Uno's training and decoding to the looped architecture.
  2. How much training is necessary? We compare 31M tokens against the 14.7B of the released recipe, and two learning rates.
  3. Does the speedup reach agentic work, and where does it fall short? We report function calling, agent trajectories and math, the cost of one step, and the cases that came out slower or flat.

TL;DR

  • A looped model can be accelerated by diffusion drafting. We extend Uno's training and decoding to looped stacks, and one LoRA trains through both loops.
  • One hour of training is enough for a 1.5–2× speedup. Function calling decodes 1.98× faster, agent trajectories 1.58× and math 1.47×, with the original model's accuracy. The adapter never saw a tool call in training.
  • The speedup is a trade-off between token acceptance and step cost. A step keeps 2.04 tokens and costs 1.29 standard steps. Each drafted position is accepted with probability about 0.54, and the first rejection ends the step. This caps tokens per step near 2.2.

Background

Draft with an adapter, verify with the original model

  • AR decoding is standard decoding: one forward pass yields one token.
  • A block is the group of positions drafted together. Our block size is 8.
  • A decode step is one draft pass followed by one verify pass.
  • Tokens per forward (TPF) is the average number of tokens a decode step keeps. AR decoding has TPF 1.00.

Uno keeps the base model frozen. It adds one LoRA that is active only on noise rows, the positions that hold a mask token and wait to be drafted. In the draft pass the model with the LoRA fills all 8 positions of the block at once. In the verify pass the original model, with the LoRA off, checks the 8 guesses and keeps the longest prefix it agrees with. The first position always receives the exact AR token, so every step emits at least one token. The verification rule is lossless: the output follows the original model's distribution exactly.

Training is self-distillation

Each training sequence enters the batch twice. The clean copy goes through the frozen model and acts as the teacher. The block-noised copy goes through the model with the LoRA and acts as the student. The loss is the total-variation (TV) distance between the two next-token distributions on the response tokens. Under lossless verification a drafted token is accepted with probability 1 − TV, so the loss is the quantity decoding depends on. The dataset labels are never used. The data only supplies realistic contexts.

What the loop costs

Nanbeige4.2-3B reads its weights twice per token, like a model of about 6.3B parameters. One AR step takes 28.8 ms. Qwen3-8B takes 28.9 ms. Each extra token per step therefore saves a full double pass.

Q1: Does diffusion drafting fit a looped model?

The answer is yes. Uno was designed for models that run each layer once per token. Our contribution is to extend it to the looped architecture, in training and in decoding.

Looped training. Uno's training code was written for Qwen3. We extended it to run a looped stack: the layers run twice per token, and the final norm closes each pass, as in Nanbeige4.2. With this change the model inside Uno's code gives the same outputs as the official Nanbeige4.2.

A LoRA that works in loop mode. The two passes share their weights, so the drafting LoRA sits on weights that every token uses twice. We train one LoRA through both passes. It is active in both and learns from both. It needs no loop-specific parameters and keeps the shape of the released adapter.

Looped decoding. The draft-and-verify decoder now supports looped models. A layer sees different inputs in its first and second pass, so the decoder keeps one cache per pass while the weights stay shared.

The released learning rate works and takes four times longer

With the released learning rate of 1e-5 the same model reaches TPF 1.75 at step 60 and 2.04 at step 260, after 3.8 hours. The run ends at 2.05 after 300 steps. Both learning rates end in the same range. A learning rate of 1e-4 gets there in about a quarter of the time.

The plateau

Both curves flatten near 2.2 tokens per step. Verification keeps a prefix: the first rejected position ends the step, and every draft after it is discarded. Suppose each position is accepted with the same probability. A step then keeps the first token, plus the second with that probability, plus the third only if the second survived, and so on. Each further position counts for less.

On math a drafted position is accepted about half of the time. At that rate the tail of the block is almost never reached, so a larger block would add almost nothing. The headroom lies in the acceptance rate, which measures how well the model's own next tokens can be predicted several positions ahead. Function calls are easier to predict, and they keep more tokens per step.

So one hour buys most of what this recipe gives on this model.

Q3: Does the speedup reach agentic work, and where does it fall short?

One Uno step costs 1.29 AR steps

Measured on 1 GPU with 4 sequences at temperature 1.0. All our evaluations run with CUDA graphs. At small batch, decoding time is dominated by reading the weights, so drafting 8 rows costs little more than 1. A step that costs 1.29× needs TPF above 1.29 to break even. We call TPF ÷ 1.29 the per-step estimate of the speedup.

The adapter transfers to tool calls without seeing any. Function calls are highly structured, and they reach the highest TPF of the three tasks.

Accuracy follows the original model. On BFCL the AR decoder scores 87.2% and Uno 87.5%. On gsm8k the AR decoder scores 96.0% and the Uno checkpoints score between 93.0% and 96.0%. The gsm8k runs sample at temperature 1.0 on 200 problems, where the standard error is about 1.7 points.

Where it falls short

Early checkpoints are slower than AR. After 7 minutes of training the model keeps 1.40 tokens per step and decodes at 0.91× of AR speed. The per-step estimate puts break-even at TPF 1.29. End to end, the first checkpoint that beats AR has TPF 1.62 and runs at 1.13×. In the run with learning rate 1e-5, a checkpoint with TPF 1.75 measured 1.02×.

Measured speed trails the per-step estimate. At TPF 2.04 the estimate is 1.58× and the measurement is 1.47×. At TPF 2.18 the estimate is 1.69× and the measurement is 1.45×. The gap comes from the tail of each batch. A few long sequences keep running after the others finish, and the GPUs are underfilled during that time.

More training raised TPF and left gsm8k speed flat. From 52 minutes to 3.5 hours TPF rises from 2.04 to 2.18. Measured speed moves from 1.47× to 1.45×. The agentic tasks do gain: BFCL moves from 1.98× to 2.10× and SWE replay from 1.58× to 1.62×.

Single timings are noisy. In the run with learning rate 1e-5, the five checkpoints with TPF between 1.94 and 2.05 measured between 1.09× and 1.48×. TPF is the stable number in this post. Each tok/s value comes from one pass over 200 problems.

TPF stops at 2.2. The acceptance rate is about 0.54, against 0.64 for the released Qwen3-8B adapter.

Practical guidance

  • Check parity first. Compare logits with the official implementation under the attention backend used in training. Self-distillation hides a wrong port.
  • Look for a norm inside the loop. For a looped model, find out whether the final norm closes every loop.
  • Start with one stage. A fixed block size of 8 and learning rate 1e-4 gave TPF 2 in one hour here.
  • Stop early. On this model, training past one hour bought 0.14 TPF in three hours.
  • Measure the step cost. Break-even TPF is the cost ratio of one step. End to end, expect to need more.
  • Report TPF and tok/s together. TPF is stable across runs. tok/s decides whether users see a speedup.
  • Expect more on structured output. Function calls gained the most.

Limits of this study

  • The agentic results score single function-calling turns and replay recorded trajectories. The actions are generated and never executed, so SWE replay measures speed only.
  • Each gsm8k point uses 200 problems and one timing pass.
  • BFCL accuracy uses a simplified AST checker, applied identically to both decoders. Absolute scores may differ from the official leaderboard.
  • The study covers one looped model.

Reproduce

Code and every script behind the numbers above are on GitHub. The adapters are on Hugging Face. The path from a fresh clone to the tables is six commands:

python nanbeige/build_uno_model.py models/nanbeige42_3b_uno 166107   # assemble the model folder
bash loopuno/prep_data.sh                                            # tokenize 60k OpenThoughts3 conversations
bash loopuno/train.sh                                                # 60 steps, lr 1e-4, block 8
bash loopuno/eval_gsm8k.sh checkpoints/loopuno-b8-lr1e-4             # TPF, tok/s, accuracy per checkpoint
bash loopuno/agentic/run_all.sh checkpoints/loopuno-b8-lr1e-4/checkpoint-60
python loopuno/bench_step_cost.py nanbeige 8 graph                   # per-step cost, AR vs Uno
